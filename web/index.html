Control & observation path

Process boundaries
  1. 01
    Browser

    Plain HTML, CSS, and JavaScript. One-second sampling; no synthetic telemetry.

  2. 02
    Python HTTP API

    Loopback-only FastAPI service. Input validation, session protection, and exclusive test ownership.

  3. 03
    Python test harness

    pytest runs in a supervised child process. Live phase reports, JUnit XML, and bounded execution.

  4. 04
    gRPC / Protocol Buffers

    Typed commands and telemetry. Explicit RPC deadlines. No Python imports of simulator internals.

  5. 05
    C++ hardware abstraction layer

    IDevice and ITelemetryProvider separate control code from the simulator implementation.

  6. 06
    Generic optical module & instruments

    Synchronized state machine, periodic telemetry, optical power meter, attenuation, and thermal inputs.

Manual commands go directly from the API to gRPC. Validation goes through the Python harness and then the same gRPC service.

Behavior worth inspecting

  • Boundary conditions

    RX at −20 dBm remains valid; below it asserts loss of signal. Thermal protection trips at 85 °C.

  • Recovery with an interlock

    Cooling does not acknowledge a latched fault. Clearing a fault does not automatically enable TX.

  • Timeout isolation

    A delayed telemetry call cannot hold the device lock or prevent recovery commands.

  • Coherent snapshots

    State and telemetry share a mutex. Concurrent reads cannot observe TX enabled with disabled-TX power.

Verification, without overclaiming

C++ GoogleTest checks deterministic components. Python checks the complete compiled service. CI is configured for Ubuntu and Windows, with Linux static analysis and sanitizers.

This console reports local execution only. It does not claim hosted CI has passed or that physical hardware has been validated.
